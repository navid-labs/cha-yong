## 한 줄 결론

토스페이먼츠 에스크로는 **차량 승계처럼 물리 배송이 없는 거래에는 원래 맞지 않는 상품이다** — 공식 문서가 "신용카드, 콘텐츠(실물거래가 없는 거래)는 에스크로 의무 적용 대상이 아니"라고 명시하고, 배송정보 등록 흐름은 택배사·운송장번호를 전제로 설계돼 있다[확인]. 차용 코드는 이 상품을 아예 켜지 않은 채(`useEscrow` 파라미터가 코드베이스 어디에도 없음) UI에서만 "토스페이먼츠 에스크로로 안전하게 결제됩니다"라고 표시한다[코드] — 다만 **결제 승인 자체는 서버에서 Toss 승인 API로 직접 검증하고, 검증 수단(`TOSS_SECRET`) 없이 PG 증빙만 오면 오히려 거절하는 fail-closed 게이트가 이미 구현돼 있다**(`src/lib/payment/toss.ts`)[코드, 4ff4412 기준 — 이전 조사가 본 구 커밋 0f8e775에는 이 검증이 TODO 상태였다]. 차량번호 조회는 경쟁사(카딩)가 이미 쓰는 자동조회 경로가 있는데[2차, 경쟁사 지형 §1.4/§2.1] 차용은 (이전엔 5종 목업 배열을 반환했으나 지금은) 정직하게 503을 반환하는 미구현 스텁이다[코드]. 본인인증·소유자 일치 확인은 자동화 수단을 조사했지만, 차용은 Q26/Q28 결정대로 자동차등록원부 업로드 + 매니저 수동 검증 노선을 이미 확정했고 이는 합리적인 선택이다 — 국토부 공공데이터 API도 카히스토리 B2B 제휴도 초기 물량(매물당 1건)에서는 쓰기 어렵기 때문이다[확인].

**경쟁사가 차량번호로 자동입력하는지** [2차, bench 백업 문서 인용]:

- **이어카**: 개인정보처리방침 위탁업체 목록에 오토비긴즈가 "차량정보조회" 명목으로 있음(경쟁사 지형 §1.4) — 등록 폼 자체에서 자동조회 UI를 직접 확인하지는 못함.
- **다이어트카·리스트레이드·자승카·승계다이렉트·승계고**: 백업 문서(bench-out/{dietcar,leasetrade,community,agency}.md)를 "차량번호", "자동 조회", "carNumber"로 grep한 결과 자동조회 UI 언급 없음 — 모두 차량번호를 매물 필드로만 노출("일치" 대응 표기)하고, 조회 자동화 여부는 명시하지 않음.
- 결론: **자동조회 UI가 원문으로 확인되는 곳은 카딩 하나**다. 나머지는 필드 매핑만 확인됐고 자동화 여부는 미확인.

## 2. 토스페이먼츠 에스크로 (+ 대안)

### 2.1 이용 자격·법적 근거

- **에스크로 의무 대상**: 전자상거래법 시행령(2006-02-22 확정)에 따라 10만원 이상 결제는 소비자가 에스크로를 선택할 수 있어야 하고, 2013년부터 5만원 미만 현금 결제도 보호 대상이 됐다. **통신판매업 신고를 하는 모든 사업자는 원칙적으로 에스크로 의무 적용 대상**이다[확인, docs.tosspayments.com/resources/glossary/escrow].
- **의무 적용 제외(핵심)**: "신용카드 거래는 카드사에서 지급을 정지시킬 수 있어요. 콘텐츠 거래는 실물 제품이 없어서 배송 기간이 없어요. **그래서 신용카드, 콘텐츠 거래는 에스크로 의무 적용 대상이 아니에요.**"[확인, 원문 인용, 같은 문서]. NHN KCP도 동일 근거를 전자상거래법 24조 3항으로 인용한다: "정보통신망으로 전송되거나 에스크로 사업자가 배송을 확인할 수 없는 재화 등을 구매하는 거래"는 적용 예외[확인, developer.kcp.co.kr/guide/escrow].
- **Toss 자체 권고**: "실제 '물품'이 거래되지 않는 콘텐츠의 경우 송장번호가 나오지 않아 배송추적이 어렵기 때문에 **에스크로 서비스 가입을 추천하지 않아요.** 통신판매업 신고를 위해 가입은 하더라도 실제 서비스 사용은 한 번 더 생각해 보시는 게 좋아요."[확인, 원문 인용, tosspayments.com/blog/articles/semo-4]. 차량 승계는 상품 배송이 없는 거래이므로 이 권고의 대상에 정확히 해당한다[판단].
- **가맹 계약**: 에스크로는 표준 계약과 별도로 "추가 계약"이 필요하며 고객센터(1544-7772)를 통해 신청한다. 계약 후 상점관리자에서 결제수단별로 켜야 하고, 홈페이지 하단에 에스크로 인증 마크 부착이 필요하다[확인, escrow glossary]. 가맹 심사 서류·제한 업종 목록은 로그인 온보딩 뒤에 있어 원문으로 확인 못함[미확인].
- **구매안전서비스 이용확인증**: 통신판매업 신고 시 필요한 서류이며, 은행(기업은행·국민은행)이나 PG사에서 발급받는다[확인, semo-4]. 즉 인과관계가 반대다 — 차용이 통신판매업 신고를 하려면 먼저 에스크로(또는 은행 구매안전서비스)에 가입해 확인증을 받아야 한다.

## 4. 차용 코드와의 간극

> 이 절은 워크트리를 `4ff4412`(브랜치 fix/codebase-audit-gaps, 2026-09-15) 기준으로 리베이스한 뒤 코드를 다시 읽고 작성했다. 결제 검증 쪽은 이전 조사(구 커밋 `0f8e775`) 대비 상당히 보강돼 있었다 — 아래에서 "이전 조사 정정"으로 표시한 세 항목은 삭제·정정한다.

### 4.1 에스크로 결제 (`src/features/payment/`, `src/app/api/payment/`, `src/lib/payment/`, `src/app/(protected)/payment/`)

1. **`useEscrow`가 코드베이스 전체에 없다 (핵심 발견, 유지).** `useEscrow`·`escrowProducts`를 `src/`와 `prisma/schema.prisma` 전체에서 grep해도 0건이다. `escrow-checkout.tsx:85-93`의 `requestPayment` 호출에도, `EscrowPayment` 스키마에도 이 상품을 켜는 값이 없다. UI 카피("토스페이먼츠 에스크로로 안전하게 결제됩니다", `escrow-checkout.tsx:264`; 결제 페이지 메타데이터 "에스크로 방식으로 안전하게 결제하세요", `payment/[listingId]/page.tsx:17`)는 여전히 실제 API 요청과 무관하다. §2의 결론(카드·무배송 거래는 에스크로 의무 대상이 아니고 Toss 자신도 비권장)과 겹쳐 보면, 지금 코드는 사실 이 권고를 그대로 따른 상태(에스크로 미사용)이면서 카피만 에스크로를 표방하는 셈이다.
2. **SDK 호출 형태는 v2 가이드와 정확히 일치한다 — 이전 조사 정정, "v1식 호출·런타임 깨짐" 주장 삭제.** 현재 코드(`escrow-checkout.tsx:83-93`)는 `tossPayments.payment({ customerKey: buyerId })`로 결제 객체를 먼저 만들고, `tossPayment.requestPayment({ method: "CARD", amount: { currency: "KRW", value: totalAmount }, orderId, orderName, customerName, successUrl, failUrl })`을 호출한다. 이는 공식 v2 통합 가이드(`docs.tosspayments.com/guides/v2/payment-window/integration`)의 예제와 구조·필드명이 일치한다. 남은 차이는 세부일 뿐이다: 가이드 예제는 `customerEmail`·`customerMobilePhone`도 함께 보내는데 차용은 보내지 않고, `customerName`에 사람 이름 대신 `buyerId`(UUID)를 그대로 넣는다 — 결제창에 표시되는 주문자명이 UUID로 보일 수 있다.
3. **서버 검증은 이미 구현돼 있고 fail-closed 게이트까지 있다 — 이전 조사 정정, "TODO·클라 신뢰" 주장 삭제.** `src/lib/payment/toss.ts`의 `verifyTossPayment()`가 Toss 결제 승인 API(`POST https://api.tosspayments.com/v1/payments/confirm`)를 서버에서 직접 호출해 `status === "DONE"`, `orderId` 일치, `totalAmount` 일치를 모두 검증한다. `confirm/route.ts:45-73`은 `TOSS_SECRET` 존재 여부로 분기한다 — 시크릿이 있으면 검증을 반드시 통과해야 `PAID`로 전이하고, 시크릿이 없는데 `pgPaymentKey`/`pgOrderId`가 오면 오히려 **거절**한다(클라이언트가 검증 수단 없이 PG 증빙을 위조해 우회하는 공격을 막는 fail-closed 설계, 400 반환). 시크릿도 PG 증빙도 없을 때만 개발 모드로 스킵된다. 이 구현은 공식 결제 승인 API 문서(§2.2 core-api-reference의 `POST /v1/payments/confirm`)와 정확히 맞는다.
4. **`successUrl`/`fail` 라우팅은 정상이다 — 이전 조사 정정, "405 위험" 주장 삭제.** `successUrl`은 이제 API 라우트가 아니라 페이지(`src/app/(protected)/payment/success/page.tsx`)를 가리킨다. Toss가 `paymentKey`·`orderId`를 GET 쿼리로 붙여 이 페이지로 리다이렉트하면, 페이지가 클라이언트에서 `fetch("/api/payment/confirm", {method:"POST", ...})`로 다시 호출한다 — GET 리다이렉트 목적지와 POST 호출 목적지가 분리돼 있어 메서드 불일치가 없다. `fail/page.tsx`도 `code`/`message` 쿼리를 받아 표시하는 별도 페이지로 존재한다. `res.ok || res.status === 409`를 성공으로 간주해 새로고침·중복 콜백도 멱등 처리한다.
5. **정산 필드가 비어 있다 (유지).** `EscrowPayment.platformFee`/`pgFee`는 스키마에 있지만 `prepare/route.ts`가 생성 시 채우지 않는다(현재도 동일). Q34가 정한 "빠른승계 정액 30만원 + PG 수수료 매도자 차감" 로직이 아직 결제 준비 단계에 연결돼 있지 않다.
6. **수수료 수치 (유지)**: Q34는 "~3.3%"로 적었지만 공식 공시는 카드 일반 3.4%(+VAT), 에스크로를 실제로 켜면 +0.2%p다. 정산 로직을 구현할 때 이 차이를 반영해야 한다.
7. **배송 등록/구매확정 개념 자체가 코드에 없다 (유지, 논지 조정).** 있는 상태 머신은 `PENDING → PAID → RELEASED/REFUNDED/DISPUTED`(EscrowPayment)와 `transferProofKey` 업로드 + 매니저 수동 검증(Q28, `src/lib/payment/escrow.ts`의 `canViewEscrow`는 이 증빙의 열람 권한만 판정)이다. 이는 Toss 에스크로의 "배송 등록 → 구매확정" 개념과 다른, 차용 자체의 대체 검증 절차이며 — 결제 검증 자체는 이번에 확인했듯 견고하다. §2의 결론과 겹쳐 보면 **"에스크로"라는 이름을 이 자체 검증 절차와 UI 카피에 계속 쓸지, Toss의 실제 에스크로 상품(`useEscrow`)을 켤지, 아니면 명칭만 다른 안전결제로 갈지는 여전히 결정이 필요한 지점**이다. 이 문서는 후보만 제시하고 결정하지 않는다.

### 4.2 차량번호 조회 (`src/features/sell/components/plate-lookup.tsx`, `src/app/api/sell/plate-lookup/route.ts`)

1. **더 이상 목업 데이터를 반환하지 않는다 — 이전 조사 정정.** 이전엔 `MOCK_POOL`(BMW X3 등 5종)을 번호판 해시로 골라 마치 실제 조회인 것처럼 반환했으나, 현재 `route.ts`는 그 코드를 걷어내고 형식 검증만 통과하면 **항상 503**과 "번호판 자동 조회는 현재 제공되지 않습니다. 차량 정보를 직접 입력해주세요."를 반환한다. 코드 주석이 이유를 직접 밝힌다: "사용자의 실제 번호판과 무관한 차량을 prefill 하여 잘못된 매물 정보를 유발했다(조작 데이터). 정직하게 503을 반환". `plate-lookup.tsx`의 `!res.ok` 분기가 이미 "조회에 실패했습니다. 수동으로 입력해주세요."로 우아하게 감싸므로 UX가 깨지지는 않는다. **다만 이 문서 §1의 조사 결과(외부 API로 대체할 수 있는 후보: 국토부 자동차종합정보, 카히스토리, 오토비긴즈)는 여전히 유효한 다음 단계다** — 지금은 그 어떤 것도 연동돼 있지 않다는 사실 자체는 바뀌지 않았다.
2. **`src/openapi/vehicles.yaml`과의 불일치는 그대로 남아 있다 (유지).** `GET /vehicles/lookup-plate`가 `DEALER 또는 ADMIN만 가능`이라고 명시돼 있고 `PlateResult` 스키마(brand/model/year/fuelType/engineCC 등)도 정의돼 있다. 그런데 실제 구현은 `POST /api/sell/plate-lookup`이고 역할 제한이 없으며 이제는 항상 503만 반환한다 — OpenAPI 문서와 실제 라우트가 경로·메서드·권한·동작 모두 다르다. 이 openapi 파일이 미래 설계도인지 과거 설계의 잔재인지부터 확인이 필요하다(§5 참조).
3. **경쟁사(카딩) 대비 (유지)**: 카딩은 차량번호 자동조회 + 소재지 좌표 입력까지 등록 폼에서 끝낸다(§1). 차용은 형식 검증(`PLATE_RE`)만 실제로 동작하고, 그 다음은 "제공되지 않음" 안내다 — 이전엔 가짜 데이터, 지금은 정직한 실패로 바뀌었을 뿐 실제 조회 기능은 여전히 없다.

### 4.3 본인인증·소유 검증

- 코드에 PASS/NICE/KMC/Toss 본인인증 연동이 전혀 없다(`본인인증`, `PASS`, `NICE`, `KMC` grep 결과 무관 파일만 히트). Supabase Auth(이메일/소셜)만 있고, 이는 "이 사람이 실존 인물"임을 증명할 뿐 "이 사람이 이 차량의 소유자"임을 증명하지 않는다.
- Q26/Q28의 문서 업로드 + 매니저 수동 검증 노선은 §3에서 확인했듯 현재로선 가장 현실적인 방법이라 **간극이라기보다 확정 사실**에 가깝다. Phase 2에서 자동화를 검토한다면, 이번 조사가 찾은 후보는 (a) 바로써트류 리셀러의 본인인증 API(30원/건대)로 "매도자 본인 확인"만 자동화하고 (b) "소유자=매도자 일치"는 여전히 서류 대조로 남기는 절충안이다[판단].
